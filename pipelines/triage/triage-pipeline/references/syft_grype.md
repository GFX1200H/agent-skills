Syft-Grype Scanner
1. Overview
This tool is a containerized scanner that uses syft to generate a Software Bill of Materials (SBOM) and grype to perform a vulnerability scan (SCA - Software Composition Analysis). It is designed to be used as a quality gate in a CI/CD pipeline.
This container enforces security standards by failing the CI job if any vulnerabilities are discovered that have not been explicitly mitigated in a configuration file.
2. Usage in GitLab CI
To use this scanner, specify it as the image for a job in your .gitlab-ci.yml. You must provide the NAME of your application, which is used to locate the project directory to scan.
Example .gitlab-ci.yml Job:
syft_grype:
  stage: scans
  image: path/to/your/syft-grype-container:latest
  variables:
    # Name of the application/service being scanned
    NAME: "my-app"
    # Optional: Path to the configuration file
    CDSO_CONFIG_PATH: "cdso_config.yml"
  script:
    - scan
  artifacts:
    when: always
    paths:
      - syft_grype.json
      - syft_grype-sbom.json
3. Configuration
The scanner's behavior is controlled by CI/CD variables and a YAML configuration file.
3.1. CI/CD Variables
   Variable    Description    Required/Default   NAMEThe name of the application. Used to locate the project directory to scan and to find the correct configuration key in the YAML file.RequiredCDSO_CONFIG_PATHPath to the YAML configuration file for the scanner.Defaults to cdso_config.yml  
3.2. cdso_config.yml
This file allows you to customize the scanner's execution and mitigate specific findings. The scanner uses the NAME variable to find the correct configuration block.
Example cdso_config.yml:
# cdso_config.yml
my-app:
  mitigations:
    # A dictionary of findings to mitigate.
    # The key is the vulnerability ID (e.g., CVE, GHSA).
    # The value is the reason for the mitigation, written in three labelled
    # sections. The scanner splits them apart so the cDSO report can give each
    # its own column -- see 4.1.
    - "CVE-2023-4567": >-
        Vulnerability Response: Mitigated
        Description: This CVE affects a component not used in our execution path.
        Mitigation: The vulnerable code path is unreachable in this container.
    - "GHSA-abcd-1234-wxyz": >-
        Vulnerability Response: False Positive
        Description: The vulnerable function is only used in development environments.
        Mitigation: Development tooling is not present in the production image.
Recommended mitigation format
Use all three labelled sections for every new or updated mitigation. This is the
same canonical format printed in every syft_grype job, so it can be copied
straight into the matching application's mitigations list.

Vulnerability Response: is the canonical action label. Use one of
Mitigated, False Positive, POA&M, or Won't Fix.
Description: explains why the finding applies or does not apply to the
application.
Mitigation: records the remediation, compensating control, or where that
protection is documented.

Accepted aliases and normalized values
Labels are case-insensitive and can appear in any order. The parser accepts the
following compatibility aliases, but new entries should use the canonical
labels above:
   YAML label    Parsed report field    Accepted aliases   Vulnerability Response:actionAction:, Response:Description:mitigation_descriptionJustification:Mitigation:mitigationNone  
The canonical response values are also case-insensitive. POAM is normalized
to POA&M, and wont fix is normalized to Won't Fix. Any other response
value of 40 characters or fewer is preserved as a custom action value; it may
not meet a project's configured mitigation-format policy.
Fallback behavior

An unlabelled mitigation, or text before the first recognised label, is
stored in mitigation and receives an Unspecified action.
If text following an action label is longer than 40 characters and is not a
recognised response value, it is stored in mitigation_description and the
action is Unspecified.
For a finding without a matching mitigation, the scanner sets action to
Unmitigated only when the finding exceeds the configured risk tolerance;
otherwise it is suppressed from the unmitigated report section.

4. Outputs

syft_grype-sbom.json: The raw SBOM generated by syft.
syft_grype-raw-output.json: The raw vulnerability report generated by grype from the SBOM.
syft_grype.json: The parsed report cDSO renders in the merge request.

4.1. Reported vulnerability fields
Each vulnerability in syft_grype.json carries the mitigation split into its
own fields, so the cDSO report can give each its own column instead of printing
one unreadable blob:
   Field    Source   cveThe vulnerability ID.severitySeverity as reported by grype.actionThe response declared through Vulnerability Response:, Action:, or Response:. Canonical values are Mitigated, POA&M, False Positive, and Won't Fix; normalized aliases and short custom values are preserved as described above. Unspecified is used for fallback justifications, and Unmitigated is assigned by the scanner when no qualifying mitigation exists.descriptionThe CVE description from grype, rendered as Grype Description in the cDSO report.mitigation_descriptionThe author's Description: or Justification: section, rendered as User Description in the cDSO report.mitigationThe author's Mitigation: section. An unlabelled justification or text before the first recognised label lands here whole.  
5. Debugging
If the CI job fails, download the syft_grype-raw-output.json artifact and identify the findings with a status of "UNMITIGATED". For each one, you can either:

Update the vulnerable package to a non-vulnerable version.
Add the vulnerability ID (e.g., "CVE-...") to the mitigations section of your cdso_config.yml with a justification.

6. Grype Database
The grype database is cached locally in the container at /app/.grype. This cache is updated nightly within cDSO to remove network dependencies at runtime.
Unmitigated Vulnerabilities
If the syft_grype job gives an error referring to an unmitigated vulnerability. This means that your application has a program with a known vulnerability. You must mitigate or justify the vulnerability in order for the job to pass. Options are:

Patch the program to use a non-vulnerable version.
Write an appropriate mitigation statement in the syft-grype cdso_config.yml. This statement is reviewed by the authorizers for your app and they have the right to decide whether or not it's good enough justification to approve. For example to mitigate CVE-2024-45336:

image_name:
  ...
  mitigations:
    - CVE_2024_45336: >-
        Vulnerability Response: Mitigated
        Description: The HTTP client drops sensitive headers after following a cross-domain redirect. For example, a
        request to a.com/ containing an Authorization header which is redirected to b.com/ will not send that header to
        b.com. In the event that the client received a subsequent same-domain redirect, however, the sensitive headers would
        be restored. For example, a chain of redirects from a.com/, to b.com/1, and finally to b.com/2 would incorrectly
        send the Authorization header to b.com/2.
        Mitigation: The HTTP client should not restore sensitive headers after following a cross-domain redirect. This container also
        has a connection context of NONE and therefore won't be reaching out to use this http client anyways.
Catalog-controlled automatic suppression
The supported scan entrypoint selects one security-group-owned control file from the ordered SECURITY_CONTROL JSON variable. Each entry is [server_fqdns, upstream_project_globs, filename]; the first entry matching CI_SERVER_FQDN and UPSTREAM_CI_PROJECT_PATH is used. The selected file must be beneath catalog/security_groups/security_controls. An invalid mapping, unsafe path, missing selected file, or no match disables automatic suppression rather than falling back to application-local policy.
[[["code.levelup.cce.af.mil"], ["organization/*"], "test_platform.yml"]]
A selected control provides syft_grype windows for critical, high, and medium findings. min_CVE_published_time applies to recently published CVEs; min_KEV_publish_time applies to recently added KEV entries. Manual mitigations take precedence. CVE_EMERGENCY_BLOCK_LIST is a protected, comma-delimited, uppercase-CVE list that blocks automatic suppression for listed findings. Low and unknown findings remain default exclusions unless emergency-blocked.
When Grype omits a CVE publication date, the scanner read-only queries NVD rows in the bundled Grype v6 database. Raw Grype data remains authoritative, and an absent or incompatible database grants no suppression. EPSS scores and CVSS vectors are reported as informational risk context only; they do not suppress findings.
